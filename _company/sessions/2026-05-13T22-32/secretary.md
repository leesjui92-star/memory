### 🎯 최우선 표준화 목표: 마스터 데이터 스트림 오케스트레이션 레이어 구축 (Message Queue 기반)

**목표 정의:** 모든 핵심 데이터를 비동기 메시지 큐(Asynchronous Message Queue, 예: Kafka/RabbitMQ 개념 도입)를 통해 전송하고 처리하는 단일 아키텍처 계층을 구축합니다. 이를 통해 개별 컴포넌트 간의 의존성을 완전히 분리하고(Decoupling), 시스템 부하가 높아져도 데이터 유실 없이 안정적으로 데이터를 주고받는 '운영 신뢰성'을 확보할 수 있습니다.

**기대 효과:**
*   ✅ **강건성 (Resilience):** Rate Limit 초과나 일시적 API 장애 시, 메시지가 큐에 쌓여있다가 성공하면 재처리되어 데이터 손실이 없습니다.
*   ✅ **확장성 (Scalability):** 새로운 기능(예: 리포팅 모듈)을 추가할 때 기존 시스템 코드를 건드릴 필요 없이 '리스너'만 연결하면 됩니다.
*   ✅ **가시성:** 모든 데이터 흐름이 중앙 큐를 거치며 기록되므로, 문제 발생 지점을 즉각적으로 추적할 수 있습니다.

### 🏗️ WBS (Work Breakdown Structure) 초안 및 개발 리소스

**총 예상 기간:** 3주 (전문 에이전트 투입 시점부터 측정)
**필수 참여 에이전트:** Developer/Developer, Kodari, 영숙(Secretary - 아키텍처 설계 및 문서화 총괄)

#### Phase 1: 설계 및 계약 정의 (Week 1)
*   **WBS-1.1: 마스터 스키마 정의 (Schema Definition):** 시스템에서 주고받는 모든 데이터 타입(Raw Data, Processed Insight, Blueprint Signal 등)에 대한 JSON 표준 페이로드(Payload) 스키마를 최종 확정합니다.
    *   *결과물:* `Master_Data_Schema_v1.0.json` (모든 에이전트가 준수해야 할 데이터 계약서).
*   **WBS-1.2: 큐 토픽(Topic) 및 흐름 매핑:** 각 주요 프로세스 단계별로 필요한 메시지 큐 토픽 목록과 메시지 전송/수신 순서를 도식화합니다.
    *   *결과물:* `Data_Flow_Diagram.png` & `Message_Queue_Topology.md`.

#### Phase 2: 구현 및 인터페이스 개발 (Week 2)
*   **WBS-2.1: Message Producer 모듈 구축:** 각 데이터 소스(스크립트, API 호출 결과 등)가 데이터를 큐에 넣는 표준화된 'Producer' 클래스를 제작합니다. (예: `auto_planner.py` $\rightarrow$ Queue).
    *   *책임:* Kodari/Developer (코드 적용)
*   **WBS-2.2: Message Consumer 모듈 구축:** 데이터를 수신하여 다음 단계의 로직을 수행하는 표준화된 'Consumer' 클래스를 제작합니다. 이는 기존 스크립트를 큐를 구독(Subscribe)하도록 리팩토링하는 작업입니다.
    *   *책임:* Developer (코드 적용 및 테스트)

#### Phase 3: 통합, 테스트 및 문서화 (Week 3)
*   **WBS-3.1: End-to-End 통합 시뮬레이션:** 실제 데이터 흐름을 재현하여, 메시지 전송 $\rightarrow$ 수신 $\rightarrow$ 로직 처리까지의 전체 파이프라인 안정성을 검증합니다.
    *   *책임:* Kodari/Developer (테스트 주도)
*   **WBS-3.2: 운영 매뉴얼 및 에러 핸들링 정의:** 큐 시스템의 모니터링 방법, 실패 시 재처리 정책(Retry Policy), 그리고 서비스 장애 발생 시 대응 절차를 문서화합니다.
    *   *책임:* 영숙 (문서화)
