### 🛠️ Knowledge Ingestion Gateway API 스키마 업데이트

아래는 **입력(Input)**과 **출력(Output)** 스키마의 재설계입니다. 특히, 입력에는 원본 데이터 외에 불안정 요소를 명시적으로 레이블링하는 필드를 추가하고, 출력에는 계산된 KRS 점수를 포함하도록 설계했습니다.

#### 1. API 입력 스키마 (`/ingest`)

새로운 입력 스키마는 원본 데이터를 수집할 뿐만 아니라, 잠재적 불안정 요소에 대한 초기 분석을 요청하는 구조로 변경됩니다.

```json
{
  "source_type": "string (필수)",
  "raw_data": "string (필수) - 크롤링된 텍스트 또는 API 응답의 원본 데이터",
  "context_metadata": {
    "ingestion_date": "datetime (필수)",
    "source_url": "string (선택)",
    "original_schema": "object (선택) - 만약 입력된 데이터에 구조가 있다면 포함"
  },
  "initial_risk_assessment": {
    "keywords": "array<string> (선택) - 사용자가 미리 지정한 위험 키워드",
    "semantic_complexity_score": "float (필수) - 텍스트의 복잡도/전문성 점수 (0.0 ~ 1.0)",
    "emotional_load_estimate": "float (필수) - 텍스트에 내포된 감정적 부하 추정치 (0.0 ~ 1.0)"
  }
}
```

#### 2. API 출력 스키마 (`/process`)

출력 스키마는 단순한 데이터 반환을 넘어, **KRS(Uncertainty Element Score)** 점수와 구체적인 불안정 요소 레이블링 정보를 포함하도록 설계됩니다.

```json
{
  "ingestion_id": "string (필수) - 이 인스턴스를 식별하는 고유 ID",
  "processed_data": {
    "original_text_summary": "string (필수) - 원본 데이터의 요약본",
    "structured_entities": "array<object> (필수) - 추출된 핵심 엔티티 목록 (이름, 유형, 위치 정보 포함)",
    "extracted_facts": "array<object> (필수) - 추출된 사실 및 데이터 포인트",
    "risk_analysis": {
      "krs_score": "float (필수) - 최종 불안정 요소 점수 (0.0 ~ 10.0)",
      "uncertainty_elements": "array<object> (필수) - 구체적인 불안정 요소 목록",
      "risk_labels": "array<string> (필수) - 레이블링된 위험 카테고리 (예: Financial_Instability, Trend_Volatility, Data_Gap)",
      "confidence_level": "float (필수) - 모델이 해당 분석에 대해 가지는 자신감 수준 (0.0 ~ 1.0)"
    }
  },
  "pipeline_status": {
    "status": "string (필수) - 'SUCCESS', 'PARTIAL_FAIL', 'ERROR'",
    "error_details": "string (선택) - 오류 발생 시 상세 내용"
  }
}
```

### ⚙️ 백엔드 로직 업데이트 방향

`backend/services/knowledge_ingestion_gateway.py` 내의 핵심 처리 함수는 다음과 같이 업데이트되어야 합니다:

1.  **Input Validation & Pre-processing:** 입력된 `initial_risk_assessment` 필드를 사용하여, 단순 수집이 아닌 '불안정성' 중심의 초기 프롬프트를 생성합니다.
2.  **KRS Calculation Module:** 새로운 모듈을 추가하여 `raw_data`와 `context_metadata`, 그리고 `initial_risk_assessment`를 기반으로 `krs_score`를 산출하는 로직을 구현합니다. 이 점수는 `semantic_complexity_score`와 `emotional_load_estimate`의 가중치를 반영해야 합니다.
3.  **Entity & Fact Extraction:** 기존의 정보 추출(NLP) 단계에, 레이블링된 위험 카테고리(`risk_labels`)를 포함하도록 제약 조건을 추가하여, 데이터가 구조화될 때 불안정 요소가 명확히 분리되도록 합니다.

기존의 데이터 파이프라인은 수집된 데이터를 단순 저장하는 데 초점을 맞추었다면, 이제는 **'불안정성 점수화(KRS)'**라는 핵심 지표를 중심으로 구조화해야 합니다.

#### 1.1. 입력 스키마 (Input Schema) 강화 방안
Knowledge Ingestion Gateway가 외부 소스(YouTube Data API, 웹 크롤링 결과)로부터 데이터를 받을 때, 단순히 원본 데이터를 받는 것을 넘어 **'불안정성 레이블링 정보'**를 포함하도록 구조를 변경해야 합니다.

| 필드명 | 타입 | 설명 | 필요성 (KRS 연관) |
| :--- | :--- | :--- | :--- |
| `source_id` | String | 원본 데이터의 고유 식별자 (URL, Video ID 등) | 추적성 확보 |
| `raw_content` | String | 수집된 원본 텍스트 또는 데이터. | 정보 제공 |
| **`risk_labels`** | JSON Array | LLM/크롤링을 통해 도출된 불안정 요소 레이블 (예: `[Source_Error]`, `[Data_Inconsistency]`). | **핵심 지표화** |
| `ingestion_timestamp`| DateTime | 데이터가 시스템에 수집된 정확한 시간. | 시계열 분석 |
| `ingestion_status` | Enum | 현재 파이프라인 처리 상태 (`PENDING`, `SUCCESS`, `FAILED`, `REVIEW_REQUIRED`). | **실패 관리** |

#### 1.2. 출력 스키마 (Output Schema) 강화 방안
Gateway가 최종적으로 Knowledge Base에 데이터를 저장할 때, LLM 호출 실패 시에도 시스템이 정상적으로 작동하고 오류를 명확히 전달하기 위한 구조가 필요합니다.

| 필드명 | 타입 | 설명 | 필요성 (재구축 목표) |
| :--- | :--- | :--- | :--- |
| `record_id` | UUID | 데이터베이스의 고유 레코드 ID. | 영구 식별자 |
| `processed_data` | JSON | 최종 정제된 내용 및 **KRS 점수** 포함. | 분석 기반 제공 |
| `krs_score` | Float | 전체 불안정 요소 점수 (0.0 ~ 100.0). | 행동 유도 지표 |
| **`pipeline_log`** | Array of Object | 각 단계별 처리 과정과 오류 기록. (`step`, `status`, `error_message`). | **디버깅 및 추적** |
| `llm_failure_status`| Enum | LLM 호출 성공 여부 (`SUCCESS`, `LLM_ERROR`, `SKIP_DUE_TO_RISK`). | 실패 상황 명시 |

### 2. LLM 호출 실패를 고려한 데이터 파이프라인 재구축 방안 (Error-Resilient Pipeline)

LLM 호출 실패는 전체 파이프라인의 병목이 될 수 있으므로, **Retry 메커니즘**과 **분기 처리(Branching Logic)**를 통합하여 시스템을 안정화해야 합니다.

#### 2.1. 단계별 오류 관리 로직 정의 (Step-wise Error Management)

데이터 흐름은 다음과 같이 분기되어야 합니다:
$$\text{Ingestion} \rightarrow \text{Validation} \rightarrow \text{KRS Tagging} \rightarrow \text{LLM Processing} \rightarrow \text{Final Storage}$$

1.  **Step 1 & 2 (Ingestion & Validation):** 이 단계에서 발생하는 오류는 즉시 `ingestion_status`를 `FAILED`로 설정하고, `pipeline_log`에 상세 오류 메시지(`error_message`)와 함께 기록합니다. 이는 수집된 원본 데이터가 유실되지 않도록 보장합니다.
2.  **Step 3 (KRS Tagging):** 이 단계는 LLM 호출이 아니므로 성공/실패 여부가 명확하며, 실패 시에는 `risk_labels` 필드에 시스템 오류를 기록하고 다음 단계로 넘길 수 있도록 허용합니다.
3.  **Step 4 (LLM Processing - Critical Point):**
    *   **Retry Logic:** LLM API 호출 실패 시, 기본적으로 **Exponential Backoff** 전략을 사용하여 최대 $N$회 재시도(예: 3회)를 수행합니다.
    *   **Failure Branching:** 모든 재시도 후에도 실패할 경우, `llm_failure_status`를 `LLM_ERROR`로 설정하고, 데이터베이스 레코드의 상태를 `REVIEW_REQUIRED`로 변경합니다. 이는 자동화된 루프가 멈추는 것을 방지하고 **수동 검토(Human-in-the-Loop)** 프로세스로 전환을 유도합니다.

#### 2.2. 백엔드 구현 제안 (Code Implementation Focus)

`backend/services/google_ai.py` 내의 Polling 및 Retry 로직에 위에서 정의된 실패 분기 로직을 통합해야 합니다.

**구현 상세:**
1.  API 호출 함수 내부에 `try...except` 블록을 강화하여 네트워크 오류, Rate Limit 오류, 모델 응답 오류 등을 구체적으로 포착합니다.
2.  실패 시, 예외 객체를 단순히 던지는 대신, 해당 예외를 **JSON 형식의 구조화된 에러 메시지**로 변환하여 `pipeline_log`에 기록하도록 로직을 수정합니다. (이것이 데이터 파이프라인의 안정성을 보장하는 핵심입니다.)
3.  최종 저장 시, LLM 실패 여부(`llm_failure_status`)를 명시적으로 플래그로 설정하여, 후속 작업(예: Business 에이전트가 데이터를 처리할 때)이 이 데이터가 '신뢰할 수 없는' 상태임을 즉시 인지하게 합니다.

**파일:** `backend/services/google_ai.py` (업데이트 및 확장)

```python
import os
import time
from google import genai
from google.genai.errors import APIError

# --- 환경 변수 설정 (보안 준수) ---
# API 키는 환경 변수에서 로드됨 (os.environ.get('GEMINI_API_KEY'))

class KnowledgeIngestionGateway:
    """
    Knowledge Ingestion Gateway API를 처리하는 핵심 클래스.
    데이터 파이프라인의 안정성과 LLM 호출 실패 대비 Retry 메커니즘을 포함합니다.
    """
    def __init__(self, model_name: str = "gemini-2.5-pro", max_retries: int = 5, initial_backoff: float = 1.0):
        # LLM 클라이언트 초기화
        self.client = genai.Client()
        self.model_name = model_name
        self.max_retries = max_retries
        self.initial_backoff = initial_backoff
        print(f"KnowledgeIngestionGateway initialized with model: {self.model_name}")

    def _retryable_call(self, prompt: str, attempt: int) -> str:
        """
        LLM 호출을 시도하고 실패 시 지수 백오프(Exponential Backoff)를 사용하여 재시도하는 내부 함수.
        """
        if attempt > self.max_retries:
            print(f"🚨 [FATAL] LLM 호출 실패. 최대 재시도 횟수({self.max_retries}) 초과. 최종 실패.")
            raise Exception("LLM Call Failed after maximum retries.")

        try:
            print(f"Attempt {attempt}/{self.max_retries}: Calling LLM API...")
            # 실제 LLM 호출 로직 (예시)
            response = self.client.models.generate_content(
                model=self.model_name,
                contents=prompt
            )
            return response.text
        
        except APIError as e:
            print(f"⚠️ [Warning] LLM API 호출 중 오류 발생 (Attempt {attempt}): {e}")
            if attempt < self.max_retries:
                # 지수 백오프 계산: backoff = initial_backoff * (2 ** (attempt - 1))
                wait_time = self.initial_backoff * (2 ** (attempt - 1))
                print(f"⏳ 재시도 대기 중... {wait_time:.2f}초 후 재시도.")
                time.sleep(wait_time)
                # 재귀적으로 다시 호출
                return self._retryable_call(prompt, attempt + 1)
            else:
                # 최대 재시도 실패 시 예외 발생
                raise

    def ingest_data_with_retry(self, input_data: dict) -> str:
        """
        데이터를 받아 KRS 점수 분석을 수행하고 안정적으로 결과를 반환합니다.
        이 함수는 데이터 파이프라인의 핵심 안정화 지점입니다.
        """
        # 1. 입력 데이터 구조 검증 (KRS 스키마 준수 확인)
        if 'krs_score' not in input_data or 'risk_factors' not in input_data:
            raise ValueError("Input data missing required KRS fields (krs_score, risk_factors).")

        # 2. 프롬프트 구성 (불안감 극대화 전략 반영)
        system_prompt = (
            "당신은 구조적 위험 폭로 전문가입니다. 제공된 데이터를 기반으로 '구조적 불안감'을 극대화하는 분석 보고서를 생성해야 합니다. "
            "결과에는 반드시 KRS 점수와 함께, 각 위험 요소가 어떻게 시스템의 결함을 유발하는지 상세히 진단하고, 행동을 촉구하는 CTA를 포함하십시오."
        )
        user_prompt = (
            f"다음 데이터로 분석하시오:\n"
            f"KRS Score: {input_data.get('krs_score')}\n"
            f"Risk Factors: {input_data.get('risk_factors')}\n\n"
            "구조적 위험 폭로 보고서를 작성하세요."
        )

        # 3. 안정적인 LLM 호출 실행 (Retry 로직 적용)
        try:
            result = self._retryable_call(user_prompt, attempt=1)
            return result
        except Exception as e:
            print(f"❌ 최종 데이터 처리 실패: {e}")
            # API 실패 시, 데이터 파이프라인에 오류 로그를 기록하고 실패 데이터를 반환하거나 예외를 다시 발생시킴.
            raise RuntimeError("Data Ingestion Pipeline Failed.") from e

# --- 실행 테스트 예시 ---
if __name__ == '__main__':
    # 환경 변수 설정 확인 (실제 환경에서는 이 부분이 자동으로 처리되어야 함)
    if not os.getenv("GEMINI_API_KEY"):
        print("🚨 GEMINI_API_KEY 환경변수가 설정되지 않았습니다. 테스트를 건너뜁니다.")
    else:
        try:
            # 가상의 입력 데이터 (Business 에이전트가 제공할 KRS 점수)
            test_data = {
                "krs_score": 85,
                "risk_factors": ["높은 자본 요구사항", "시장 변동성", "규제 불확실성"]
            }

            gateway = KnowledgeIngestionGateway(model_name="gemini-2.5-pro", max_retries=3)
            print("\n--- 데이터 파이프라인 테스트 시작 ---")
            
            final_report = gateway.ingest_data_with_retry(test_data)
            
            print("\n✅ 최종 결과 수신 완료:")
            print("=========================================")
            print(final_report)
            print("=========================================")

        except Exception as e:
            print(f"\n🛑 시스템 실행 중 치명적인 오류 발생: {e}")

```

## 🎬 최종 비주얼 시스템 및 제작 요구사항 (Production Blueprint)

Writer가 제시한 스크립트 흐름(Flow)과 레오가 정의한 심리적 불안감 극대화 원칙을 통합하여, 실제 영상 제작에 즉시 적용 가능한 **최종 비주얼 시스템 가이드라인**을 아래와 같이 정리합니다. 이 가이드는 모든 썸네일 및 영상 내 자막/연출에 대한 절대적인 기준이 됩니다.

---

### I. 브랜드 비주얼 핵심 원칙 (The Core Mood)

모든 영상 콘텐츠는 다음의 심리적 불안감을 극대화하는 시각 언어를 사용해야 합니다.

1.  **색상 팔레트 (Color Palette):**
    *   **주조색 (Primary):** Deep Black (`#0A0A0A`) 또는 Very Dark Gray (`#151515`) - 깊은 밤, 미스터리감 부여.
    *   **강조색 (Accent/Warning):** Neon Cyan / Electric Blue (`#00FFFF` 또는 `#007BFF`) - 시스템 오류, 디지털 통제, 경고를 상징.
    *   **보조색 (Secondary):** Dark Gray (`#333333`), Muted Red (`#FF4500`) - 긴장감과 위험을 강조하는 데 사용.

2.  **타이포그래피 시스템 (Typography System):**
    *   **폰트 계열:** 고대비의 산세리프체 (Sans-serif). 불안감이나 기계적 느낌을 주는 폰트(예: *Orbitron*, *Space Mono*, 또는 시스템 환경에 맞는 고정폭 폰트)를 사용합니다.
    *   **규칙:** 모든 핵심 정보는 **고대비(High Contrast)** 처리를 통해 시각적 충격을 주어야 합니다. (주조색 위에 강조색을 배치).

3.  **레이아웃 원칙 (Layout Principles):**
    *   **구도:** 인물의 클로즈업 또는 시스템의 복잡한 데이터 구조를 표현하는 미니멀하고 대칭적인 구도를 선호합니다.
    *   **공간 활용:** 화면의 대부분을 어둠(Black Space)으로 처리하여 강조색 요소에 시선이 집중되도록 합니다. (Glassmorphism 효과 적용 권장).

---

### II. 영상 구간별 비주얼 요구사항 (Sequence-Specific Visual Requirements)

다음은 Writer가 제시한 스크립트의 흐름에 따라 각 구간에서 적용되어야 할 구체적인 디자인 지침입니다.

#### 1. 🔥 HOOK (0~3초: 시선 장악 단계)
*   **목표:** 즉각적인 충격과 질문을 던져 이탈 방지.
*   **비주얼 지침:**
    *   **배경:** 완전한 블랙 배경 (`#0A0A0A`).
    *   **텍스트/자막:** **Neon Cyan** 색상을 사용하여, 굵고 날카로운 애니메이션(Strobe 또는 Glitch 효과)으로 등장시킵니다. 자막은 화면 중앙 하단에 배치하되, 경고 표시(`!`, `ERROR`)를 강조색으로 사용합니다.
    *   **사운드 연동:** 사운드의 가장 큰 피크 지점과 텍스트 애니메이션의 최고 속도를 완벽히 일치시켜야 합니다.

#### 2. 🔍 문제 제기 (4~15초: 정보 제시 단계)
*   **목표:** 시스템의 존재와 데이터의 통제라는 불안감을 논리적으로 구축.
*   **비주얼 지침:**
    *   **배경:** 어두운 회색 계열 (`#151515`).
    *   **연출:** 복잡한 코드, 그래프, 데이터 흐름(Flow) 애니메이션을 화면 전체에 오버레이합니다. 이 데이터는 정적인 이미지가 아닌, **실시간으로 움직이는 시스템의 내부**처럼 보이게 연출해야 합니다. (Designer 메모리 기반: '관제 센터' 스타일의 미니멀한 UI 요소 활용).
    *   **강조:** 핵심 키워드(KRS 점수, 통제 영역)는 강조색(`Neon Cyan`)으로 하이라이트 처리하여 시청자가 집중해야 할 지점을 명확히 제시합니다.

#### 3. 💡 CTA/클라이맥스 (36~50초: 행동 유도 단계)
*   **목표:** 수동적인 관찰자에서 능동적인 참여자로 전환 유도.
*   **비주얼 지침:**
    *   **전환:** 긴장감 있는 BGM이 갑자기 멈추고 **극도의 침묵(Silence)** 상태로 전환됩니다. 이는 시청자의 심리적 공백을 유발합니다.
    *   **행동 유도:** 마지막 문구("지금 바로 댓글로 '진실'을 남기세요.")는 명확하고 차분한 흰색/밝은 회색 폰트로 처리하여, 혼란 속에서 유일하게 제시되는 **명령**처럼 보이게 합니다.
    *   **엔딩 화면:** 채널 로고 및 다음 콘텐츠 링크(CTA)를 최소한의 정보만으로 깔끔하게 배치합니다.
